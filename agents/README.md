# agents/ · 告警研判 Agent

给一条告警，自动查日志、查该 IP 的全部告警、查情报、查资产，然后给出研判结论。

```
$ python -m agents.demo --index 0

待研判告警：命令注入 / critical / 153.117.32.249

  [1] get_log_context({'ip': '153.117.32.249', 'limit': 15})
  [2] list_alerts_by_ip({'ip': '153.117.32.249'})
  [3] check_ip_intel({'ip': '153.117.32.249'})
  [4] get_asset_info({'ip': '153.117.32.249'})

研判结果（4 步）
  结论    : true_positive
  置信度  : 0.92
  依据    : 命中利用类规则 ['cmdi_sep']，日志中有对应 payload，该 IP 共 2 次请求
  建议处置: 立即封禁并排查是否已被成功利用
```

---

## 为什么做蓝方而不是红方

| | 红方 Agent | 蓝方 Agent |
|---|---|---|
| 合规风险 | 高（自动化攻击） | 无 |
| 面试追问 | 「会不会被滥用」 | 「怎么防幻觉」 |
| 与现有项目 | 无关联 | 直接复用日志引擎 |
| 真实需求 | 弱 | 强（SOC 分析师每天几百条告警） |

红方 Agent 的技术含量不比蓝方高，但解释成本和风险都更高。
而蓝方 Agent 的难点（幻觉、可追溯、误判代价）恰好是安全场景最核心的问题。

---

## 架构

```
告警（来自 detector）
   ↓
Agent 循环（loop.py）
   ├ 系统提示词：研判规则 + 禁止推测
   ├ 每次只调一个工具
   └ 终止条件：调 submit_verdict / 步数上限 / 模型给文本
   ↓
工具集（tools.py，纯函数，可单测）
   ├ get_log_context     看原始请求
   ├ list_alerts_by_ip   看该 IP 全部告警
   ├ check_ip_intel      情报归属（当前是 mock）
   └ get_asset_info      资产重要性（当前是 mock）
   ↓
结论 + 完整 trace（每一步调了什么、返回什么）
```

三个文件各管一件事：

| 文件 | 职责 | 为什么分开 |
|---|---|---|
| `tools.py` | 工具实现 | 能脱离模型单测。出问题时能回答「是模型错了还是数据错了」 |
| `loop.py` | 循环与终止 | 换模型不用改循环，换循环不用改模型 |
| `llm.py` | 模型适配 | Mock 和真实模型共用同一套循环，行为可对比 |

## 五个设计决定

### 1. 用原生 function calling，不用 ReAct

ReAct（让模型输出 `Thought: ... Action: ...`）需要正则解析模型输出，
模型稍微不听话就崩。现在模型原生支持结构化工具调用，返回 JSON，稳定得多。

### 2. 每次只允许调一个工具

一次调多个会让 trace 变成一团，出问题无法定位是哪一步错了。
**可解释性优先于速度**——研判场景下，分析师要能复现推理路径。

### 3. 工具返回值都带 `source` 字段

模型编造结论时最常见的表现是「引用了一个工具没返回的数据」。
有了 `source`，就能比对「结论里提到的事实」是否真的来自某个工具。

这是防幻觉的第一道闸，比在提示词里写「不要编造」有效得多。

### 4. 工具异常一律转成观察结果，不抛给模型

```python
def call(name, args):
    try:
        return fn(**args)
    except Exception as exc:
        return {"error": f"工具执行失败: {exc}"}
```

工具抛异常直接冒泡，整个 agent 就崩了。
转成 `error` 返回后，模型能自己决定「换个工具」还是「报告数据不足」。

### 5. 有 MockLLM

三个理由：

- 循环逻辑的 bug 不该靠调真模型来发现，太慢太贵
- 演示不能依赖网络和余额
- **评估需要稳定基线**：如果 mock 和真模型结论差很多，说明提示词有问题，不是模型笨

MockLLM 不是固定脚本——它会**真的读工具返回值**再决定下一步。
工具返回空数据时，它会给出 `needs_investigation` 而不是硬编一个结论。

## 结论分三档，不是两档

```python
true_positive         确认是攻击
false_positive        确认是误报
needs_investigation   证据不足
```

**第三档是刻意加的。** 只给「是/不是」会逼模型在两个错答案里选一个，
而安全场景里「说不准」是合法且有价值的结论——它把人引到需要人工看的地方。

置信度低于 0.5 时基本都落在这一档。

## 当前局限（必须说清）

| 局限 | 影响 | 怎么补 |
|---|---|---|
| `check_ip_intel` / `get_asset_info` 是 mock | 情报和资产信息不真实 | 接 GeoLite2 本地库 + CMDB |
| 只研判单条告警 | 看不到跨告警的攻击链 | 做「告警聚类 → 聚成一簇再研判」 |
| 没有评估集 | 不知道准确率多少 | 人工标注 100 条告警做基准 |
| MockLLM 的判定是规则写的 | 它不是「AI」，只是行为基线 | 真模型要单独评估 |

**最后一条最重要。** MockLLM 的结论来自我写的规则，不能当成 agent 的能力证明。
真要说得清 agent 好不好，需要标注集 + 准确率/误判率。

---

## 怎么接真模型

```bash
export DEEPSEEK_API_KEY=sk-xxx
python -m agents.demo --llm --index 0
```

用的是 OpenAI 兼容格式，换其他模型只要改 `base` 和 `model`。
`temperature=0`——研判要可复现，不要创造性。

## 测试

```bash
python tests/test_agent.py
```

20 项，测的是**边界行为**不是具体文案：

- 利用类告警 → 置信度 ≥ 0.9 且建议封禁
- 扫描类告警 → 置信度更低且建议只记录（**不误封**）
- 无日志的 IP → 不下硬结论
- 死循环 → 被步数上限截断，不崩
- 工具异常 → 返回 error 不崩溃
- trace → 步数一致、可序列化

为什么测边界不测文案：换模型、换温度、换提示词，具体措辞都会变，
但「该封的封、不该封的不封、不知道的说不知道」这三条不能变。

## 交互与批量

```bash
# 单条研判 + 追问
python -m agents.app chat --index 0

# 批量研判（按 IP 聚合）
python -m agents.app batch --limit 10

# 接真实模型
export DEEPSEEK_API_KEY=sk-xxx
python -m agents.app chat --index 0 --llm
```

追问支持：`为什么` / `处置步骤` / `误判风险` / `加白名单会怎样`。

### 批量为什么按 IP 聚合

实测 81 条告警来自 21 个 IP，其中一个 IP 单独贡献了 56 条。

逐条研判等于拿同一个 IP 问模型 56 遍，结论几乎一样，纯浪费 token。
而且分析师关心的是「这个 IP 有没有威胁」，不是「第 37 条告警对不对」。

所以批量模式先按 IP 聚合，取该 IP 最严重的那条告警作代表，只研判一次。

### 一个字符串分类的坑

最初用 `"封禁" in action` 判断是否要封禁，结果「暂不封禁」也被算成要封——
**否定词和肯定词在字符串里长得一样**。

修法是先排除否定表述再判肯定，顺序不能反：

```python
negations = ("暂不封禁", "不封禁", "不建议封禁", "无需封禁", "避免封禁")
if any(n in action for n in negations):
    return False
return "封禁" in action
```

这跟内容检测里「规则只能抓已知写法」是同一类问题：
用字符串匹配做语义判断，永远有想不到的反例。
